# Supervising several autonomous coding agents without context switching: batched question digests + urgent escalation

Research date: 2026-09-06. Every claim below was verified by fetching the cited page during this session. Claude Code version-to-date mappings come from the npm registry publish times for `@anthropic-ai/claude-code` (latest at time of writing: 2.1.263, published 2026-09-06). Anything dated June–September 2026 is marked **[Jun–Sep 2026]**.

---

## 0. Bottom line

1. **Nothing does "hourly digest of agent questions + immediate escalation for urgent items + route answers back to the right agent" out of the box for Claude Code (or, as far as this research found, for any coding agent).** Every tool found either (a) fires immediately per event (ccgram, claude-remote-approver, Remote Control, cmux, Discord/Slack bridges), (b) is a passive inbox you poll (Multica, Paperclip approvals, agent view, `claude agents --json`), or (c) has severity tiers but no digest (Gas Town). The one project explicitly built as a "single queue for questions from parallel agents" (`ask-user-questions-mcp`) batches OS notifications but has no schedule and no urgency classes.
2. **The primitives to build it exist and are documented**, mostly shipped March–September 2026: PreToolUse `defer` (2.1.89, 2026-03-31), `updatedInput` answers for `AskUserQuestion` (2.1.85, 2026-03-26), Agent SDK `canUseTool` for `AskUserQuestion`, the `agent_needs_input` Notification type (2.1.198, 2026-07-01), `claude agents --json` with `waitingFor` (2.1.162, 2026-06-03), cross-session messaging + `notify_when_idle` (2.1.224/2.1.236, Aug 2026), channel permission relay (2.1.234, 2026-08-17), and `--permission-prompts none` (2.1.259, 2026-09-02).
3. The usual substrate (Ralph loops, Symphony-style tracker polling) is **deliberately question-free**: Ralph "decides, doesn't ask"; Symphony has no blocked state and relies on the tracker + next poll cycle; the official `ralph-wiggum` plugin has no human check-in at all.

## 1. Anthropic-native mechanisms (Claude Code CLI + Agent SDK)

### 1.1 How a question or blocker can be captured

| Mechanism | What it captures | Evidence (verified) |
|---|---|---|
| **`AskUserQuestion` tool** | 1–4 multiple-choice questions, each `{question, header (≤12 chars), options[2–4]{label,description}, multiSelect}`; answers returned as `answers: {"<question text>": "<label>"}` plus optional free-text `response`. | https://code.claude.com/docs/en/agent-sdk/user-input ; hooks reference "AskUserQuestion" input table https://code.claude.com/docs/en/hooks |
| **PreToolUse hook on `AskUserQuestion` → `updatedInput`** | Hook reads `tool_input.questions` from stdin, returns `hookSpecificOutput.permissionDecision: "allow"` **plus** `updatedInput: {questions, answers}`. "Returning `allow` alone is not sufficient for these tools." Added in **2.1.85 (2026-03-26)**. Decision precedence when several hooks answer: `deny > defer > ask > allow`. | hooks reference (PreToolUse decision control); CHANGELOG 2.1.85 https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md |
| **PreToolUse `permissionDecision: "defer"`** (the key batching primitive) | Only in `claude -p`. Process exits with `stop_reason: "tool_deferred"` and a `deferred_tool_use: {id, name, input}` in the `result` message; the pending tool call is preserved in the transcript. Caller shows the question in its own UI, later runs `claude -p --resume <session-id>`; the same PreToolUse fires again and the hook returns `allow` + `updatedInput`. "There is no timeout or retry limit"; session stays on disk subject to `cleanupPeriodDays` (30 days default). Limits: only works when Claude made a **single** tool call that turn; `-p --resume` does **not** restore the stored permission mode (pass `--permission-mode` again); resuming in plan mode needs `--permission-prompt-tool` (2.1.246); if the deferred tool's MCP server is gone you get `stop_reason: "tool_deferred_unavailable"`. Added **2.1.89 (2026-03-31)**; OTel trace continuity fix 2.1.239 **[Aug 2026]**. | hooks reference "Defer a tool call for later"; TS SDK `SDKResultMessage.deferred_tool_use`, `terminal_reason: "tool_deferred"` https://code.claude.com/docs/en/agent-sdk/typescript |
| **Agent SDK `canUseTool` / `can_use_tool`** | Fires for tool approvals **and** `AskUserQuestion` (`toolName === "AskUserQuestion"`). Return `{behavior:"allow", updatedInput:{questions, answers}}` or `{behavior:"deny", message}`. "The callback can stay pending indefinitely… If a user might take longer to respond than your process can reasonably stay running, register a PreToolUse hook that returns the `defer` decision instead." Python needs streaming mode and a dummy `PreToolUse` hook to keep the stream open. Under the hood: CLI is launched with `--output-format stream-json --verbose --input-format stream-json --permission-prompt-tool <name>`; the CLI emits `{"type":"control_request","request":{"subtype":"can_use_tool","tool_name","input","permission_suggestions","blocked_path","decision_reason",…}}` and the host replies `{"type":"control_response","response":{"subtype":"success","request_id","response":{"behavior":"allow","updatedInput":…}}}`. | user-input doc; permissions doc https://code.claude.com/docs/en/agent-sdk/permissions ; Python SDK source `_internal/query.py` (handles `control_request` subtypes `can_use_tool`, `hook_callback`, `mcp_message`) and `types.py` (`SDKControlPermissionRequest`) https://github.com/anthropics/claude-agent-sdk-python ; bug #34046 (Mar 13 2026, closed not planned) documents `--permission-prompt-tool stdio` https://github.com/anthropics/claude-code/issues/34046 |
| **`PermissionRequest` hook** | Fires the moment a permission dialog would open (Notification `permission_prompt` only fires after ~6 s idle). Input: `tool_name`, `tool_input`, `permission_suggestions[]`. Output: `decision: {behavior: allow/deny, updatedInput, updatedPermissions}`. "In sessions that can't show a prompt, such as background subagents in non-interactive mode, Claude Code still runs these hooks, and if no hook returns a decision, it denies the tool call." | hooks reference "PermissionRequest" |
| **`Notification` hook** | Types: `permission_prompt` (after ~6 s without typing), `idle_prompt` (~60 s after Claude finishes), `elicitation_*`, **`agent_needs_input` / `agent_completed`** (background sessions; **require 2.1.198, 2026-07-01**; fire only while `claude agents` is open in a terminal), `quota_auto_resume_*` (2.1.234). Payload: `session_id, transcript_path, cwd, permission_mode, hook_event_name, message, title, notification_type`. Hooks "can't block or modify notifications… intended for side effects such as forwarding the notification to an external service." Fires even with desktop notifications off. Fixed for Desktop/VS Code hosts in 2.1.233 **[2026-08-14]**. | hooks reference "Notification"; CHANGELOG 2.1.198, 2.1.233 |
| **`Stop` / `SubagentStop` / `TeammateIdle` / `TaskCompleted`** | `Stop` carries `last_assistant_message`; exit 2 keeps Claude working (block cap: 8 consecutive blocks). `TeammateIdle` exit 2 keeps a teammate working. | hooks reference; best-practices page https://code.claude.com/docs/en/best-practices |
| **Channels permission relay** | A two-way channel MCP server that declares `capabilities.experimental['claude/channel/permission'] = {}` receives `notifications/claude/channel/permission_request` with `{request_id (5 letters, no "l"), tool_name, description, input_preview}` and answers with `notifications/claude/channel/permission` `{request_id, behavior: 'allow'|'deny'}`. Terminal dialog stays open in parallel; first answer wins. **Relay covers tool approvals only; `AskUserQuestion` is not relayed**, and with `--channels` + `-p` "tools that need terminal input, such as multiple-choice questions and plan mode approval, are disabled." Requires 2.1.234 **[2026-08-17]** for the current gating. | https://code.claude.com/docs/en/channels-reference ; https://code.claude.com/docs/en/channels ; CHANGELOG 2.1.83 |
| **`--permission-prompts none`** (2.1.259, **2026-09-02**) | For unattended `-p` runs: anything that would prompt is denied unless a `PermissionRequest` hook allows it; **removes `AskUserQuestion` from the toolset entirely**; denials show as `permission_denied` system messages and in the result's `permission_denials`. TS SDK equivalent `permissionPrompts: 'none'`. | https://code.claude.com/docs/en/headless ; TS SDK options |
| **`askUserQuestionTimeout`** | Interactive only. Since 2.1.200 **[2026-07-03]** question dialogs no longer auto-continue by default; opt-in `60s/5m/10m` timeout submits selected options and tells Claude "you may be away… proceed on its own judgment and can re-ask later." Permission prompts never auto-resolve. | https://code.claude.com/docs/en/tools-reference ; CHANGELOG 2.1.200 |

### 1.3 Anthropic's guidance on "when Claude should ask"

- **Auto mode** (default starting mode on Pro/Max/Team) "nudges Claude to keep working without stopping for clarifying questions, though Claude still asks when your prompt or a skill explicitly relies on it." Fix in 2.1.147 (2026-05-21) so auto mode no longer suppresses `AskUserQuestion` when explicitly relied on. `AskUserQuestion` is in the "actions no mode auto-approves" list; `dontAsk` denies it even when allow-listed. https://code.claude.com/docs/en/permission-modes
- **Best practices** recommends giving Claude a verifiable check, `/goal`, a Stop-hook gate, adversarial review subagents, and "Let Claude interview you… using the AskUserQuestion tool" *before* a long run — i.e., front-load questions, don't expect them mid-run. https://code.claude.com/docs/en/best-practices
- **"Effective harnesses for long-running agents"** (2025-11-26) and **"Harness design for long-running application development"** (2026-03-24) contain **no** discussion of human check-ins or escalation; both are pure agent-to-agent handoff designs. https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents ; https://www.anthropic.com/engineering/harness-design-long-running-apps
- **"Building agents with the Claude Agent SDK"** (2025-09-29) mentions "escalating to humans when needed" only in passing. https://claude.com/blog/building-agents-with-the-claude-agent-sdk

### 2D. Ralph loops

- **Geoffrey Huntley, "Ralph Wiggum as a software engineer"** (2025-07-14): `while :; do cat PROMPT.md | claude-code ; done`. Ralph "doesn't ask for clarification — it decides"; the human's job is tuning the prompt/TODO and `git reset --hard` when it derails. https://ghuntley.com/ralph/

- **agairola/securing-ralph-loop** (4★, MIT): the only "Ralph with escalation" variant found — after 3 failed remediation attempts it opens a GitHub issue and posts a Slack webhook. Immediate, not batched. https://github.com/agairola/securing-ralph-loop

### 2E. Heartbeat / "agent company" control planes

- **Paperclip** (paperclipai/paperclip, 80.1k★, MIT; adapters: Claude Code local, Codex, Cursor, Gemini CLI, OpenCode, OpenClaw): agents run in **heartbeats** (configurable floor "e.g. every hour"; event wakes on assignment, @-mention, approval resolution). Agents raise blockers by setting issue status `blocked` with a comment "what is blocked, why, and who needs to unblock it", or `POST /api/issues/{id}/interactions` `request_confirmation` for yes/no; hires/budget/strategy go to an **Approvals queue** ("approvals don't expire on their own; agents waiting on it will pause"). Escalation follows the reporting chain; escalating to a paused manager is refused rather than silently queued. Human sees this in the dashboard; docs reference wiring Slack/Discord but describe no digest or urgency tiers. https://github.com/paperclipai/paperclip/blob/master/docs/guides/agent-developer/heartbeat-protocol.md ; https://docs.paperclip.ing/guides/org/agents/ ; https://docs.paperclip.ing/guides/welcome/key-concepts/
- **Multica** (multica-ai/multica, 49.1k★, Apache-2.0 + conditions; 26 agent CLIs incl. Claude Code): **Inbox** "for assignments, mentions, comments, and agent failures that need your follow-up"; "Get pinged when an agent needs a call, not for every step"; multiple notifications on one issue consolidate into one entry; replying to an agent's comment routes the reply to that agent for its next run. In-app only; no email/Telegram/quiet hours; no urgency tiers. Feature request #5646 (**opened 2026-07-19, open**) asks for Telegram notifications when an agent asks a clarifying question, with reply-back to the issue. https://github.com/multica-ai/multica ; https://multica.ai/docs/inbox ; https://github.com/multica-ai/multica/issues/5646
- **OpenClaw** (openclaw/openclaw, 389k★, MIT): heartbeat `every: "30m"` default (`0m` disables the cadence but keeps event wakes); `HEARTBEAT.md` is legacy — `openclaw doctor --fix` migrates it to DB-backed "monitor scratch"; suppression rule: `HEARTBEAT_OK` at start/end of reply is dropped if the remainder is ≤300 chars; `target: owner|last|none|<channel>`; agent calls `heartbeat_respond` with `notify: true` to alert. **Explicitly no urgent-vs-routine distinction.** A personal-assistant gateway, not a coding-agent supervisor. https://docs.openclaw.ai/gateway/heartbeat
- **ClaudeClaw** (moazbuilds/claudeclaw, 1.3k★, MIT; Claude Code plugin `/claudeclaw:start`): daemon with heartbeat (configurable interval, quiet hours), cron, Telegram/Discord/Slack gateway. No digest/summary scheduling described. https://github.com/moazbuilds/claudeclaw

### 2F. Codex (for comparison)

Codex app-server exposes `tool/requestUserInput` (1–3 short questions, `isOther` free-form, `autoResolutionMs` host-side timeout) and `item/commandExecution/requestApproval` etc. Responses are **blocking within the turn**; the "asynchronous questions + bounded approvals" framing found in blogs is a third-party playbook, not a documented non-blocking primitive. https://learn.chatgpt.com/docs/app-server

### 2G. Documented patterns (no code, but relevant)

- **"Run Claude Code 24/7 With an Approval Queue Pattern"** (Nathan Cole, 2026-05-12): every outbound action goes through `enqueue(type, payload)` into a JSON file; Telegram bot with Approve/Edit/Reject buttons mutates the row; a `corrections.jsonl` (last 30) is fed back as "voice calibration"; ~15–20 min/day of operator time; urgent (revenue) path bypasses the agent entirely via webhooks + DB. Pitfalls: FSEvents dropping after sleep (needs polling fallback), file locking between bot and script. https://www.roborhythms.com/autonomous-claude-code-agent-approval-queue/
- **hidekazu-konishi, "Claude Code in CI/CD and Headless Automation"** (first 2026-06-07, updated **2026-08-25**): pitfall list for unattended runs (interactive prompts stall, over-broad permissions, secrets in prompts, exit-code misreads, unbounded runtime, brittle text parsing); recommends `--max-turns`, `--max-budget-usd`, `--allowedTools`, `--permission-mode dontAsk`, pipeline `timeout`. https://hidekazu-konishi.com/entry/claude_code_cicd_and_headless_automation.html

## 3. (1) Does anything do hourly-digest + urgent-escalation out of the box?

**No.** Specifically:

- No Claude Code plugin, hook bundle, or Agent SDK sample found collects `AskUserQuestion`/permission events from several sessions and emits them on a schedule. All relays (ccgram, claude-remote-approver, Discord/Slack bridges, Remote Control push, Channels relay, cmux) are **per-event and immediate**; the only "batching" anywhere is notification suppression (ccgram active-threshold, claude-notifications-go quiet windows) or OS-notification coalescing (ask-user-questions-mcp).
- The tools that *do* aggregate (Multica inbox, Paperclip approvals, `claude agents`) are **pull-based inboxes** with no scheduled delivery and no urgency classes.
- The only urgency policy found is **Gas Town's** severity → channel mapping (mail / email / SMS, 4-hour stale re-escalation), and it has no digest for the routine tier.
- The only "questions from parallel agents in one queue" project (**ask-user-questions-mcp**) blocks the asking agent, has no schedule, and has no escalation.
- Anthropic's own direction is the opposite of batching: make the agent *not* ask (auto mode nudge, `--permission-prompts none`, background agents that open a draft PR instead of stopping), and push per event to the phone (Remote Control) when it must.

## 4. (2) The most credible building blocks for implementing it on Claude Code

### Block A — `claude -p` workers + PreToolUse `defer` (best fit; no long-lived host process required)

Evidence: hooks reference "Defer a tool call for later" (2.1.89, 2026-03-31); `SDKResultMessage.deferred_tool_use`; `terminal_reason: "tool_deferred"`; CHANGELOG 2.1.89 ("headless sessions can pause at a tool call and resume with `-p --resume` to have the hook re-evaluate").

Design:
1. Run each agent as `claude -p … --output-format stream-json --permission-mode auto` (or `acceptEdits` + allowlist). Keep `AskUserQuestion` available (do **not** pass `--permission-prompts none`, which removes the tool).
2. Register a `PreToolUse` hook matching `AskUserQuestion` (and optionally `PermissionRequest` for risky tools). The hook looks up a queue file keyed by `session_id` + `tool_use_id`; if no answer yet, it appends `{session_id, cwd, questions, timestamp, urgency}` and returns `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"defer"}}`. The process exits with `stop_reason: "tool_deferred"`; the question is preserved in the transcript.
3. **Urgency classification** happens in the same hook (deterministic rules on `header`/`question` text, `cwd`, tool name, or a Haiku call): urgent items are pushed immediately (ntfy/Telegram/Slack; ccgram or claude-remote-approver code can be reused), routine ones only go into the queue.
4. **Hourly digest**: a cron/launchd job (or a Routine, or `/loop 60m` in a supervisor session — beware `/loop`'s up-to-30-min jitter) renders the queue with context: the `questions` array, the tail of `transcript_path` (JSONL) for the last assistant text, `git diff --stat` in `cwd`. Deliver via email/Slack/Telegram with one reply syntax per item (`<id> <option-label-or-free-text>`).
5. **Answer routing**: write the answer into the queue and run `claude -p --resume <session_id> --permission-mode <same as before>`; the same `PreToolUse` fires, the hook now returns `permissionDecision: "allow"` with `updatedInput: {questions, answers: {"<question>": "<label or free text>"}}`. Free text is allowed as the value; `response` gives a general reply instead.
Caveats (all documented): single tool call per turn only (multi-call turns fall through to normal permission flow — pair with `--permission-prompts none`-style denial or a `PermissionRequest` hook that denies), permission mode not restored on `-p --resume`, plan mode needs `--permission-prompt-tool`, MCP servers must be re-attached, 30-day session retention.

### Block B — Agent SDK supervisor with `canUseTool` as the queue (single host process, richer control)

Evidence: user-input doc ("The callback can stay pending indefinitely… only cancels when the query is cancelled"); permissions evaluation order (AskUserQuestion always reaches the callback even with allow rules; `dontAsk` denies it); TS `permissionPrompts: 'none'` (2.1.259) for tools you never want to wait on; Python `SDKControlPermissionRequest` fields incl. `permission_suggestions`, `blocked_path`, `decision_reason`, `title`, `description`.

Design: one long-running Node/Python supervisor spawns N `query()` sessions; `canUseTool` pushes `{toolName, input, session}` onto a queue and awaits a promise; the hourly digest job drains the queue; urgent classifier resolves immediately via push. Answers resolve the promise with `{behavior:"allow", updatedInput:{questions, answers}}` (questions) or `{behavior:"allow"/"deny"}` (permissions, optionally `updatedPermissions` from `suggestions` to stop re-asking). Use the `permission_denials` on the result message as the authoritative record. Pitfalls: Python needs streaming input + a dummy `PreToolUse` hook to keep the stream open; a crash of the supervisor loses in-flight promises (mitigate with `defer` + resume from Block A); subagents can't call `AskUserQuestion`.

### Block C — Interactive/background sessions + `agent_needs_input` + `claude agents --json` (lowest effort, terminal-centric)

Evidence: Notification types `agent_needs_input`/`agent_completed` (2.1.198, 2026-07-01; only while `claude agents` is open); `claude agents --json --all` with `state` and `waitingFor` (2.1.162); `PermissionRequest` hook fires immediately; `Notification.permission_prompt` after 6 s idle; cross-session inbox socket `CLAUDE_CODE_MESSAGING_SOCKET`; Remote Control forwards both permission prompts and `AskUserQuestion` to the phone and keeps them open until answered.

Design: run agents as `claude --bg` sessions; a `Notification` hook (`agent_needs_input`) or a poller over `claude agents --json` builds the queue; the hourly digest is rendered from `waitingFor` + transcript tails; urgent items push via Remote Control's "Push when actions required" or a `PermissionRequest`/`PreToolUse` hook that blocks up to its `timeout` (command-hook default 600 s; a timed-out PreToolUse hook lets the call continue, so set it deliberately) while the phone answers (the ccgram mechanism). Answering a routine item requires `claude attach <id>` / agent-view peek or Remote Control — there is **no documented CLI to inject an answer into an interactive session's open `AskUserQuestion` dialog**, and cross-session `SendMessage` "can't answer a pending permission prompt on your behalf." This makes C good for detection and urgent escalation but weak for batched answer routing.

### Tracker-as-queue variant (Symphony/Paperclip style, agent-agnostic)

Have the agent write its question as a tracker comment and move the issue to a "Needs Input" state (Paperclip's `blocked` + comment, Symphony's handoff state, Scale's `needs-detail` label); the digest is a tracker query; the human's comment is the answer; the poller resumes the session with `--resume` when the state returns to active. Works without hooks but relies on the agent choosing to do it (prompt-enforced, not deterministic) and loses the tool-result association issue #50728 describes.

## 5. (3) Known pitfalls people report (with sources)

**Agents that never ask**
- Auto mode "nudges Claude to keep working without stopping for clarifying questions" (permission-modes doc); background agents from agent view "commit, push, and open a draft PR… instead of stopping to ask" (CHANGELOG 2.1.198); Ralph loops are designed to decide, not ask (ghuntley.com/ralph).
- `--permission-prompts none` removes `AskUserQuestion`; `dontAsk` denies it even when allow-listed; `--channels` + `-p` disables it; **subagents cannot call `AskUserQuestion`** at all (user-input doc "Limitations").
- Headless auto-resolution: issue #50728 (2026-04-19, closed "not planned") — in no-TTY Python SDK runs `AskUserQuestion` "auto-resolves immediately with empty answers in ~37 ms"; the deny workaround "loses conversational context — the answer arrives as a fresh prompt rather than a tool result." Interactive tools listed in a skill's `allowed-tools` used to be silently auto-allowed with empty answers (fixed 2.1.69). Linear-loop author: agents "struggle with ambiguous requirements… loop to the iteration cap… or hallucinate requirements" (damiangalarza; sitepoint summary).

**Agents that ask too much**
- Plan mode makes clarifying questions "especially common" (user-input doc); teammate permission prompts "bubble up to the lead, which can create friction" (agent-teams doc "Too many permission prompts"); mitigations: allowlists, `/less-permission-prompts` skill (2.1.111), auto mode, `PermissionRequest` hook policy-as-code, "Approve and remember" via `updatedPermissions`.

**Lost or mangled answers**
- Multi-select "Other" free text was silently dropped (fixed 2.1.181, 2026-06-17); `AskUserQuestion` told Claude to continue even when the free-text answer asked it to wait (fixed 2.1.216, 2026-07-20).
- Channel relay: "Claude Code applies whichever answer arrives first and closes the other" — terminal vs phone races; Telegram inline-button payload limit 64 bytes (ccgram).
- Non-permission dialogs forwarded to Remote Control expire after 5 min (`dialogExpiry`); held cross-session messages in a `-p` session expire after 5 min; `notify_when_idle` subscriptions drop after 12 h.
- `defer` is ignored (with a warning) when Claude made multiple tool calls in the turn; ntfy approver falls back to "ask" after 120 s, which stalls if no terminal is attached.
- Hook output errors used to make background sessions "wait silently" (fixed 2.1.226 by naming the hook and schema error in agent view).

**Session resume**
- `-p --resume` does not restore permission mode; plan mode needs `--permission-prompt-tool` (2.1.246); deferred tool can be `tool_deferred_unavailable` if its MCP server isn't attached; sessions are swept after 30 days; `--resume` by ID across directories only since 2.1.223.
- Agent teams: "`/resume` and `/rewind` do not restore in-process teammates"; `/loop` tasks restore only if unexpired; background bash/Monitor tasks never restore; SIGTERM leaves the turn unfinished and the permission prompt unanswered (headless doc).
- Older headless automation hit the interactive "resume?" dialog trap (aident.ai / community guides) — run with explicit `--resume <id>` or `--no-session-persistence`.

**Permission prompts blocking headless runs**
- In `-p` with no host, anything that would prompt is denied; `PermissionRequest` hooks are the only way to allow; `--permission-prompts none` (2.1.259) makes that explicit and tells Claude not to retry.
- `-p` shows no trust dialog and runs hooks/MCP from `.claude/settings.json` and `.mcp.json` in untrusted directories unless `--bare` (headless doc) — a security pitfall for fleet runners.
- `Notification.permission_prompt` only fires after ~6 s of no typing (and, before 2.1.233, not at all under Desktop/VS Code hosts); `agent_needs_input` only fires while `claude agents` is open in a terminal.
- Auto mode denials in `-p` don't stop the run; check `permission_denials` on the result. Channels relay does not cover project-trust or MCP-consent dialogs.

**Scheduling gotchas for a digest job**
- `/loop`: hourly tasks jitter up to 30 min (pick a non-`:00/:30` minute), fire only when the session is idle, expire after 7 days, and are session-scoped; Routines: 1-hour minimum, cloud-only (no local files), run as your identity with no permission prompts; `/goal` idle check-ins are capped at three per goal between your prompts (2.1.246).
- Running N sessions multiplies rate-limit consumption (agent-view doc).
