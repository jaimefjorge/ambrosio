# The "process layer" for Claude Code agents: frameworks, trackers, gates — and what pairs with superpowers

Research date: 2026-09-06. Local Claude Code: 2.1.263. Every star count, date, license, command name and quotation below was fetched during this session (GitHub via authenticated `gh api` after `api.github.com` returned 403 through WebFetch; docs via WebFetch/curl). Items that could not be confirmed are marked UNVERIFIED. Five parallel research agents covered §2–§6; §1, §7, Gas Town/Gas City and the superpowers-integration threads were verified directly.

## Executive summary

- **Nothing off the shelf gives you all of intake → written-and-accepted plan → implement → verify → acceptance → done *plus* queryable tracking *plus* many concurrent controllers.** The process plugins (superpowers, Compound Engineering, BMAD, Spec Kit, CCPM) are prompt conventions with files-in-repo state; the trackers (Beads, Backlog.md, Linear, GitHub Issues) are queryable but process-agnostic; the hard gates live in Claude Code's hook events (`TaskCompleted`, `Stop`, `SubagentStop`, `TeammateIdle`, `PreToolUse`) and in CI/branch protection.
- **superpowers 6.3.0 already covers the process well** (three-path brainstorming with mandatory human approval, spec + plan files, per-task fresh-context implementer + independent reviewer with a five-round breaker, verification-before-claims, a human decision at branch finish). What it lacks is exactly what you are asking about: an event surface (open issue #1442 since April; PR #1461 unmerged), a ticket concept with acceptance state, and cross-session coordination. Its SDD mode deliberately does *not* stop for humans mid-plan ("Rulings, not stalls").
- **Best scriptable source of truth for a supervisor daemon: Beads (`gastownhall/beads`)** — `bd ready --json`, `bd blocked --json`, custom statuses with ready/wip categories, human gates (`bd gate create --type=human`), atomic claims with leases and CAS guards (1.3.0-rc.1), an events journal, and (1.3.0-rc.1) an HTTP API. Caveats: heavy churn (v1.2.1 was retracted; 1.3.0 is still an RC), Dolt dependency, and single-writer embedded mode (run `dolt sql-server` for many agents on one machine). Gas Town / Gas City (same org; 17.9k / 1.2k stars, pushed this week) are the proof that Beads carries a many-agent supervisor with merge-queue gates and escalation. **Linear** is the best *hosted* answer (it can express all four questions in GraphQL and has an agent-session protocol with `awaitingInput`), but Anthropic ships no Linear agent, so you write the bridge (or use Cyrus). GitHub Issues works with label conventions; Backlog.md is fine for one-or-few agents; task-master is dormant.
- **Pair superpowers with a tracker + native hooks, not with another process plugin.** Compound Engineering, BMAD and Spec Kit all re-implement brainstorm/plan/implement/review. Take from them only the *ticket fields* (Compound Engineering's Verification Contract / Definition of Done; Kiro/cc-sdd's EARS acceptance criteria; BMAD's `sprint-status.yaml` state set) and put them on the bead. Enforce with `TaskCompleted`/`Stop` hooks that run the gates, `PreToolUse` guards on `git push`/`--no-verify`, CI + review bot on the PR, and a supervisor that only reads `bd … --json`.
- **New June–Sept 2026 (verified):** superpowers v6.0→6.3 (SDD rewrite, plan-scoped ledger, three-path brainstorming); Claude Code `/goal` (v2.1.139), Stop-hook block cap (v2.1.143), `claude agents --json`/`--bg` agent view, agent teams `TaskCompleted`/`TeammateIdle` gates, dynamic workflows, Task tools **off by default on new models** (v2.1.233); Beads 1.1→1.3.0-rc.1 (events journal, HTTP API, leases/CAS, retracted 1.2.1); Spec Kit v1.0.x with a YAML workflow engine and `gate` steps; BMAD v6.9–6.12 (bmad-loop, deterministic sprint status); Compound Engineering 3.12→3.24 (status-free plans, one-way publish); Linear Coding Sessions (Jun 11), Loops (Jul 20), Copilot-for-Linear (Jul 30); GitHub Issue fields GA (Jul 2), `gh` 2.94 dependency flags (Jun 10), Copilot review can satisfy required approvals (Sep 1); Claude Agent for Jira GA (Jun 18); Vibe Kanban's company shut down (Apr 10); Huly hosted shut down (Jul 20); CCPM and task-master dormant since March/April.

## 1. obra/superpowers (what you already have)

**What it is.** "A complete software development methodology for your coding agents, built on top of a set of composable skills" (README). It is a skills library plus one `SessionStart` hook that injects the `using-superpowers` bootstrap; everything else is prompt convention.

**Maker / maturity (verified 2026-09-06 via `gh api`).** Jesse Vincent (obra). 282,388 stars, 25,306 forks, MIT, created 2025-10-09, last push 2026-09-04, 339 open issues. Plugin manifest `version: "6.3.0"` (released 2026-08-12). Release cadence June–Sept 2026: v6.0.0 (06-16), v6.0.2/6.0.3 (06-17/18), v6.1.0 (06-30), v6.1.1 (07-02), v6.2.0 (07-23), v6.3.0 (08-12).

**Skills shipped (14, from `skills/`):** brainstorming, dispatching-parallel-agents, executing-plans, finishing-a-development-branch, receiving-code-review, requesting-code-review, subagent-driven-development, systematic-debugging, test-driven-development, using-git-worktrees, using-superpowers, verification-before-completion, writing-plans, writing-skills. There are no `agents/` or `commands/` directories any more (legacy `/brainstorm`, `/write-plan`, `/execute-plan` were removed in v5.1.0).

**Process it enforces (stages, in order):**
1. `brainstorming` — as of v6.3.0 a **three-path router**: *spike* (investigate, report a recommendation, no doc), *bounded* (clarify, present a short design in chat, no spec/plan file), *architectural* (explore context → clarifying questions one at a time → 2–3 approaches → design sections → **write design doc to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` and commit** → spec self-review → user reviews spec). "Every path ends with your human partner approving your intent before implementation." "The ratchet is one-way: hidden complexity discovered mid-task upgrades the path."
2. `using-git-worktrees` — detect existing isolation first, prefer the harness's native tool (`EnterWorktree`, `--worktree`), fall back to `git worktree add` under `.worktrees/`; asks for consent before creating one.
3. `writing-plans` — "Save plans to: `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`"; steps use `- [ ]` checkboxes; plans now carry a `Spec:` pointer, a Global Constraints block and a per-task Interfaces block (v6.0/6.3). Ends with an explicit menu: "1. Subagent-Driven (recommended) … 2. Inline Execution".
4. `subagent-driven-development` (SDD) — the controller dispatches a fresh implementer subagent per task, then one task-reviewer (spec compliance + code quality verdicts from a single `task-reviewer-prompt.md`), fix rounds resume the implementer (rounds ≤3) or escalate to a fresh, more capable model (rounds 4–5), a five-round circuit breaker with controller adjudication, then one whole-branch review at the end. **State lives in a per-plan ledger** at `<repo-root>/.superpowers/sdd/<plan-basename>/progress.md` whose first line names the plan; task briefs, implementer reports and review packages are files in that directory; the directory is deleted once the final review is clean ("git history is the durable record").
5. `test-driven-development` / `verification-before-completion` — "NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE"; the gate is a prose checklist (identify command → run → read → verify → claim).
6. `requesting-code-review` — "Critical issues block progress" (README).
7. `finishing-a-development-branch` — Step 1 runs the full test suite and stops if red; then presents exactly three options ("1. Merge back to <base> locally / 2. Push and create a Pull Request / 3. Keep the branch as-is") and **waits for the human's answer**. "Discard" is explicit-request-only since v6.2.0.

**Strictness.** Prompt convention only. The single hook (`hooks/hooks.json`) is `SessionStart` (matcher `startup|clear|compact`) that injects the bootstrap; it does not block anything. Enforcement is the bootstrap's "Mandatory workflows, not suggestions" language plus rationalization tables inside each skill. There is no `Stop`/`TaskCompleted`/`PreToolUse` gate.

**How work is tracked / queryability.** Files in the repo: spec markdown, plan markdown with checkboxes, and the transient SDD ledger. Nothing is machine-queryable by design; the plan's `- [ ]` boxes and the ledger's `Task <N>: complete` lines are grep-able but unversioned/informal. Open issue **#1442 "Expose lifecycle events beyond SessionStart for external integration"** (opened 2026-04-30, still open, last activity 2026-09-04, 7 comments) states the problem exactly: "Superpowers' workflow state is invisible to anything outside the agent … the only externally observable artifacts are git commits and a markdown plan file. There's no signal an external system can subscribe to." The author's goal was Beads as canonical source of truth with subagents pulling from `bd ready`. Companion PR **#1461 "lifecycle event hooks for external plugin authors"** (opened 2026-05-03) is still open/unmerged. A Sept-2026 comment on #1442 asks for a default-off `BeforeReview` / `BeforeBranchFinish` event so an out-of-tree quality gate can "fail closed" (a maintainability-gate plugin was closed as out of scope for core in #2199). Also relevant: open PR **#2183 "fix(skills): handle unavailable task tracking"** (2026-08-20) — Claude Code 2.1.233 removed the TodoWrite/TaskCreate tools on current models by default, which breaks the "create todos for the plan items" step in `executing-plans`/SDD unless you set `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`.

**Human approval points (where it stops).** (a) Brainstorming: "Get approval — STOP and wait for an explicit yes"; on the architectural path a second stop for "User reviews written spec". (b) Writing-plans: the execution-mode menu. (c) Worktree consent. (d) SDD: deliberately does **not** stop between tasks — "Continuous execution: Do not pause to check in with your human partner between tasks… Rulings, not stalls. A running plan does not wait on a human." Only four things stop it: irreversible/destructive operations, security-sensitive actions, side effects outside the worktree (merge, push to shared branch), or when "every path forward is a guess". (e) `executing-plans` (inline mode) does stop on blockers ("STOP executing immediately when: hit a blocker…"). (f) Finishing: the 3-option integration menu. (g) Test failures at finish.

**One agent or many.** Designed for **one controller session** that fans out short-lived subagents per task (SDD) or per independent problem (`dispatching-parallel-agents`, which explicitly refuses "shared state" cases). It has no notion of multiple concurrent controllers, no cross-session claim/lock on tasks, and the plan checkboxes are not a concurrency-safe store. Open PR **#1117 "Add execution orchestration skills for dependency-aware parallel execution"** (2026-04-10) proposes DAG-aware parallel task execution inside one session; unmerged. Worktree isolation is per-controller, not per-task.

**Gaps for your use case.** No external event surface (#1442); no queryable state; no ticket concept (a "task" is a plan section); approval is conversational, so a supervisor cannot detect "waiting on human" except by watching the terminal; SDD's "rulings, not stalls" policy means ambiguity gets decided by the agent and only surfaces in the ledger; the SDD workspace is deleted on success, so post-hoc audit relies on git. Verification is a prose gate, not a hook.

**What it does well that you should not duplicate.** Intake→design→spec→plan with hard conversational stops; per-task fresh-context implementer + independent reviewer with evidence files; verification-before-claims; branch finishing with a human decision. These are exactly the "plan (written and accepted) → implement → verify → review" stages; you need to add *tracking*, *acceptance state*, and *multi-controller coordination* around them, not replace them.

**Community bridge already exists.** `maslennikov-ig/template-bridge` (73 stars, MIT, last push 2026-06-09): a `unified-workflow` skill whose flow is "bd create → brainstorm → plan → TDD → review → verify → finish → bd close", wired with `SessionStart` and `PreCompact` hooks that run `bd prime`. It is a thin skill, not an event bridge — proof of the pattern, not infrastructure.

## 2. Compound Engineering plugin (Every / EveryInc)

**What it is.** Every's `compound-engineering-plugin`: 33 `ce-*` skills forming a loop — brainstorm → plan → work → (simplify → review) → compound — "the knowledge from each change is written down where the next change can read it." Authored as a Claude Code plugin and converted (`bun run convert --to <provider>`) to 14 hosts.

**Maker / maturity.** EveryInc (Kieran Klaassen, Trevin Chow). ~24.9k stars / 2.1k forks (HTML page; API 403'd for this repo), MIT. Latest release `compound-engineering-v3.24.0` (2026-08-31); last commit 2026-09-06. Roughly weekly releases (release-please).

**Process it enforces (commands, in order).** `[/ce-ideate] → /ce-brainstorm → /ce-plan → /ce-work → /ce-code-review → /ce-compound`, plus `/lfg` for the fully autonomous pipeline.
1. `/ce-brainstorm` — one question at a time; writes `plans/YYYY-MM-DD-HHMM-<type>-<topic>-plan.md` (frontmatter `artifact_contract: ce-unified-plan/v1`, `artifact_readiness: requirements-only`); "User confirmation is required before writing."
2. `/ce-plan` — three output tiers chosen at intake: Direct (summary), Chat brief, Durable (file at `docs/plans/…-plan.md`, moving `requirements-only → implementation-ready` in place). Required sections: Goal Capsule, Product Contract (R-IDs, acceptance examples, success criteria), Planning Contract, Implementation Units (stable U-IDs), **Verification Contract** ("repo-specific commands and quality gates, including which tests prove the plan"), **Definition of Done** ("global and per-unit done criteria"). "Pipeline runs, goal-driven runs, and risk surfaces (auth, payments, migrations) always produce Durable plans."
3. `/ce-work` — Phase 0 triage; Phase 1 workspace (feature branch, "write gate: only user-offered files may be edited", uses `TaskCreate/TaskUpdate/TaskList` when available); Phase 2 implementation loop ("Do not write the test and implementation in the same step"; commit per logical unit); Phases 3–4 shipping gates in order: `ce-simplify-code` → `ce-code-review` → **Residual Work Gate** → Final Validation (tests/lint) → Operational Validation Plan → `ce-commit-push-pr` → `ce-babysit-pr` (CI watch). `mode:return-to-caller` returns a structured envelope (`status: blocked, phase, blocker, recovery_path, artifact_path`) to a calling orchestrator.
4. `/ce-code-review` — 15 reviewer personas (correctness, testing, security, adversarial cross-model, previous-comments, …), risk-driven roster, compares findings "against the plan". "Report-only by default; never push."
5. `/ce-compound` — writes `docs/solutions/`; since 2026-09-02 gated on "durable knowledge".
6. `/lfg` — "Run the full autonomous shipping pipeline end-to-end, hands-off with no check-ins": plan → work → simplify → review → apply fixes → browser test → commit/push/PR → babysit → `<promise>DONE</promise>`; opens a PR "without merging."

**Strictness.** Prompt convention only. Verified: no `hooks/` directory (404), `plugin.json` has no hooks key; AGENTS.md: "Skills are goals, not state machines." Gates are prose ("completion checkpoints that block progression"; the code-review gate "requires finished review receipt or exact skip phrase"). v3.21.1 (2026-08-04) rewrote SKILL.md "around falsifiable gates" — still prose.

**Plan acceptance.** Soft. v3.12.0 (2026-06-09) introduced a "status-free plan model": "The plan itself stays read-only. Shipping status lives in git, not in the document." `/ce-work` with no args "auto-picks newest implementation-ready plan" — acceptance is the menu default, not a recorded state.

**Tracking / queryability.** Files only (`docs/plans/`, `docs/solutions/`, U-ID-prefixed commits, PR body). Ephemeral host tasks. Handoff menu offers "Create Issue — Tracked issue in the project's configured tool (GitHub, Linear, Jira, etc.)" but `docs/guides/configuration.md` documents no tracker key (UNVERIFIED how it is configured). `/ce-handoff` writes to `/tmp/compound-engineering-<uid>/…`. No CLI/JSON status query; the only structured surface is the return envelope.

**Human approval points.** ce-brainstorm: confirmation before writing. ce-plan: scoping confirmation (skippable via `confirm:auto`), then "Plan ready at <path>. What would you like to do next?" (Start ce-work / Run as `/goal` / Decide on review open items / Create Issue / Open in browser) — the agent waits. ce-work: Residual Work Gate — "Code review left N actionable finding(s) not yet fixed. How should the agent proceed?" Apply / File tickets / Accept and proceed / Stop; commit-push-pr asks before push. `mode:pipeline` and `/lfg` "skip all user asks". Trend: v3.13.1 (06-17) "replace HITL review loop with one-way publish"; v3.20.0 (07-22) "autonomous watch-loop over review, CI, and branch state".

**Single vs many agents.** `execution-strategy.md`: "Parallel subagents — the default for structured multi-unit plans"; dispatch per dependency layer, 3–5 workers per batch; Parallel Safety Check for shared types/migrations/lockfiles; "harness-managed isolated worktrees or … shared-workspace wave contract"; workers never touch the git index — "the orchestrator stages and commits after the batch." Cross-model engine (`work_engine_mode: off|prefer|require`) runs Codex/Cursor/OpenCode/Grok in `/tmp/…/ce-work/<run-id>/`. It is one orchestrator session fanning out; no cross-session coordination. Standalone `agents/` were removed (63 personas consolidated into skill-local prompts).

**Gaps.** No hooks, no state machine, no persistent work-item state, nothing queryable; plan acceptance implicit; very large and fast-moving surface (breaking `ce-` rename in v3.0.0, Apr 2026; v3.23.0 cut doc sizes 50–90%). Handoffs in /tmp.

## 4. Spec-driven frameworks: Spec Kit, BMAD, Agent OS, Kiro-style

### 4a. GitHub Spec Kit (github/spec-kit)
**What.** `specify` CLI + agent slash-commands scaffolding a Markdown pipeline: constitution → spec → plan → tasks → implement, with optional clarify/checklist/analyze/converge; since 2026 also extensions/presets and a YAML **workflow engine with human gates**.
**Maturity.** GitHub. 133,712 stars, 12,031 forks, MIT, pushed 2026-09-04, latest v1.0.4 (2026-09-02). Claude Code: `specify init <name> --integration claude` ("installs skills in `.claude/skills`").
**Process (commands verified from `templates/commands/*.md`).** `/speckit.constitution` → `/speckit.specify` (creates `specs/NNN-<short-name>/spec.md`, records path in `.specify/feature.json`, max 3 `[NEEDS CLARIFICATION]`, generates `checklists/requirements.md`) → `/speckit.clarify` (≤5 questions, "EXACTLY ONE question at a time", writes `## Clarifications` into spec.md) → `/speckit.plan` (`research.md`, `data-model.md`, `contracts/`, `quickstart.md`; Constitution Check gate pre/post design) → `/speckit.checklist` ("unit tests for requirements writing", `CHK001…`; `[x]` "does not indicate implementation completion") → `/speckit.tasks` (every task `- [ ] [ID] [P?] [Story?] Description with file path`; `[P]` = parallelizable; "Tests are OPTIONAL - only include them if explicitly requested") → `/speckit.analyze` (read-only, six checks; asks before remediation) → `/speckit.implement` (halts if any checklist has unchecked items and asks the user; executes phase by phase, marks `[X]`; halts on non-parallel failures) → `/speckit.converge` (0.11.2+; appends "Phase N: Convergence" gap tasks, never edits spec/plan/code) · `/speckit.taskstoissues` (GitHub MCP `issue_write`, titles `T001: …`, **one-way**).
**Strictness.** Prompt convention. Extension "hooks" are entries in `.specify/extensions.yml` the *agent* executes. The one tooling-level gate is `specify workflow run <id>` (step types `if, switch, while, do-while, fan-out, fan-in, command, prompt, shell, gate, init, slot`; state in `.specify/workflows/runs/<run_id>/{state.json,inputs.json,log.jsonl}`; `specify workflow resume`). Bundled `workflows/speckit/workflow.yml` ("Full SDD Cycle" v1.0.1): specify → `gate` ("Review the generated spec before planning", `options: [approve, reject]`, `on_reject: abort`) → plan → `gate` ("Review the plan before generating tasks") → tasks → implement. **No gate before implement**; clarify/checklist/analyze/converge not in the bundled workflow. v1.0.3 added `--require-spec`.
**Tracking / queryability.** `specs/<n>/tasks.md` checkboxes (regex-parsable), `checklists/*.md`, `.specify/feature.json`, workflow `state.json`/`log.jsonl`. External: GitHub Issues one-way; community **ashbrener/spec-kit-linear-sync** (v0.8.0, 4 stars, MIT) — one Linear issue per spec, sub-issue per task phase, `after_*` hook on every `/speckit.*` command; "a sub-issue's workflow state tracks the tasks.md checkbox ratio until the spec is ready_to_merge/merged." No JSON status API in core.
**Human approval.** Clarify Q&A; analyze asks before remediation; implement asks when checklists incomplete; `gate` steps in workflows. Otherwise `/speckit.implement` runs all tasks without pausing.

### 4e. Cross-cutting takeaways for this family
- Only two things here are enforced by software rather than prompt: Spec Kit's `specify workflow run` engine (`gate` steps, resumable `state.json`) and spec-workflow-mcp's MCP approval records. Kiro's own `PreTaskExecution` blocking hook is the third, but only inside Kiro.

Agent OS v3: none.
- Acceptance-criteria formalization: EARS (Kiro, cc-sdd, jasonkneen); Spec Kit user stories + acceptance scenarios + requirement-quality checklists; BMAD capabilities each with a "success condition" plus an `acceptance-auditor` review layer.

### 7a. Best practices page — the verification doctrine
- Headline tip: "Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from." "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop."
- It now explicitly ranks **how hard the check gates the stop**: (1) in one prompt; (2) across a session via a **`/goal` condition** ("A separate evaluator re-checks it after every turn"); (3) **as a deterministic gate: a Stop hook** "runs your check as a script and blocks the turn from ending until it passes. Claude Code overrides the hook and ends the turn after 8 consecutive blocks"; (4) **by a second opinion**: a verification subagent or a dynamic workflow "so the agent doing the work isn't the one grading it."
- "Have Claude show evidence rather than asserting success."
- Plan mode workflow: Explore → Plan (Ctrl+G opens the plan in your editor) → Implement → Commit; "If you could describe the diff in one sentence, skip the plan."
- "Let Claude interview you … write a complete spec to SPEC.md", then start a fresh session to execute it.
- Multi-session: worktrees, cross-session messaging, desktop, web, **agent view** (research preview), **agent teams** (experimental, off by default); Writer/Reviewer pattern; `/batch` splits one change across 5–30 worktree-isolated subagents that each open a PR; fan-out via `claude -p … --output-format json`.
- "Add an adversarial review step": a fresh-context subagent reviews the diff against PLAN.md; bundled `/code-review` skill.
- Hooks framing: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens."

### 7b. Plan mode (permission-modes page)
- "Plan mode tells Claude to research and propose changes without making them… edits stay blocked until you approve the plan." Enter with Shift+Tab, `/plan` prefix, or `claude --permission-mode plan` (also works with `-p`).
- Approval prompt options: "Yes, and use auto mode" (or "Yes, auto-accept edits"), "Yes, manually approve edits", "No, keep planning". Ctrl+G edits the plan text before proceeding. `ExitPlanMode` "Presents a plan for approval and exits plan mode"; `EnterPlanMode` exists as a tool.
- Can be made the default: `"permissions": {"defaultMode": "plan"}` in `.claude/settings.json`.
- Agent teams: "When a teammate finishes planning, it sends a plan approval request to the lead. Claude Code approves the plan in the lead's session as soon as the request arrives, without the lead reviewing it." — i.e. teammate plans are **not** human-gated.
- The docs do not describe an on-disk plan file location (plan text lives in the conversation; Ctrl+G opens it in an editor).

### 7c. Hooks — the hard-gate surface (33 events as of this doc)
Events: SessionStart, Setup, UserPromptSubmit, UserPromptExpansion, PreToolUse, PermissionRequest, PermissionDenied, PostToolUse, PostToolUseFailure, PostToolBatch, Notification, MessageDisplay, SubagentStart, SubagentStop, **TaskCreated, TaskCompleted**, Stop, StopFailure, **TeammateIdle**, InstructionsLoaded, ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate, WorktreeRemove, PreCompact, PostCompact, PreModelSwitch, PostModelSwitch, **Elicitation, ElicitationResult**, SessionEnd.
- Exit codes: "Exit code 2: Blocking error. On events that can block, exit 2 blocks regardless of JSON output. The blocking message comes from your JSON's blocking decision reason or stderr text."
- **Stop**: "Prevents Claude from stopping, continues the conversation." Input includes `stop_hook_active` ("true when Claude Code is already continuing as a result of a stop hook… Claude Code overrides the hook and ends the turn after 8 consecutive blocks"), `last_assistant_message`, and `background_tasks`/`session_crons` arrays that "let hooks distinguish 'session is done' from 'session is paused waiting for background work'". JSON `decision: "block"` + `reason`, or `additionalContext` for guidance.
- **TaskCompleted** (verbatim): "Runs when a task is being marked as completed. This fires in two situations: when any agent explicitly marks a task as completed through the TaskUpdate tool, or when an agent team teammate finishes its turn with in-progress tasks. Use this to enforce completion criteria like passing tests or lint checks before a task can close." Input: `task_id`, `task_subject`, `task_description`, `teammate_name`, `team_name` (deprecated). "Exit code 2: the task is not marked as completed and the stderr message is fed back to the model as feedback."
- **TaskCreated**: "Runs when a task is being created via the TaskCreate tool. Use this to enforce naming conventions, require task descriptions, or prevent certain tasks from being created."
- **TeammateIdle**: "Runs when an agent team teammate is about to go idle… Use this to enforce quality gates before a teammate stops working."
- **Elicitation / ElicitationResult**: "When an MCP server requests user input during a tool call" / "After a user responds to an MCP elicitation" — a hookable "waiting on human" signal, but only for MCP elicitations.
- Caveat that matters: on Opus 4.8 / Sonnet 5 / Fable 5 / Mythos 5 and later, `TodoWrite`, `TaskCreate/Get/Update/List` are **not provided unless you opt in** (`CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, `--allowedTools TaskCreate`, or `--tools`). Without them TaskCreated/TaskCompleted never fire and the task list stays empty (tools-reference, since v2.1.233).

### 7d. The built-in task list (what a supervisor can actually read)
- Task tools: `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate` (+ `TaskStop` for background tasks); `TodoWrite` is "Disabled by default in favor of" them. Lifecycle: `pending` → `in_progress` → `completed`, plus `status: "deleted"` on update (SDK todo-tracking page).
- Agent teams: "Tasks have three states: pending, in progress, and completed. Tasks can also depend on other tasks: a pending task with unresolved dependencies cannot be claimed until those dependencies are completed." "Task claiming uses file locking." "Claude Code manages task dependencies automatically."
- **On disk**: "Task list: `~/.claude/tasks/{team-name}/`" (team name = `session-<first 8 chars of session id>`); "The task list directory persists locally… so resumed sessions keep their tasks." Share across sessions with `CLAUDE_CODE_TASK_LIST_ID=my-project claude` (interactive-mode page). Verified locally: `~/.claude/tasks/<session-id>/<n>.json` files with shape `{"id","subject","description","activeForm","status","blocks":[],"blockedBy":[]}`. So a supervisor can `jq` ready work (`status=="pending" and (blockedBy|length)==0`) directly — but there is no owner/assignee, no "review"/"accepted" state, no acceptance criteria field, and no CLI to query it.
- Known limitation (agent-teams page): "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks."

### 7e. Agent teams, agent view, workflows (the many-agents surface)
- **Agent teams**: experimental, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; one lead + teammates sharing the task list and a mailbox (`~/.claude/teams/{team-name}/inboxes/{agent}.json`); "Spawning teammates also requires an interactive session" (not `-p`/SDK); "Agent teams don't isolate teammates in worktrees, so partition the work"; one team per session, no nested teams, lead fixed; quality gates via TeammateIdle/TaskCreated/TaskCompleted hooks. Human approval: teammate permission prompts bubble to the lead's terminal; plan approvals are auto-granted.
- **Agent view** (`claude agents`, research preview, v2.1.140+): "one screen for all your background sessions: what's running, what needs your input, and what's done." Groups: Needs input / Ready for review (open PR) / Working / Completed. **Scriptable**: `claude agents --json [--all] [--cwd path]` returns `{id, state: working|blocked|done|failed|stopped, cwd, kind, startedAt, sessionId, name, waitingFor}` (verified locally on 2.1.263); `claude --bg "prompt"`, `claude attach|logs|stop|respawn|rm <id>`, `claude daemon status`. Background sessions auto-move into `.claude/worktrees/`; PR status color tracks checks/review/merged.
- **Dynamic workflows** (`/workflows`, `ultracode`): a JS script orchestrates up to 16 concurrent / 1,000 total subagents; "No mid-run user input… For sign-off between stages, run each stage as its own workflow"; results in script variables; resumable; can "have independent agents adversarially review each other's findings".
- **`/goal`**: "a wrapper around a session-scoped prompt-based Stop hook"; verdicts Not yet met / Met / Impossible from the small fast model; works with `claude -p "/goal …"`; stalls stop the loop; background-work check-ins back off 30m→1h→2h (v2.1.234+).
- **Cross-session messaging** (v2.1.224+): `ListAgents`/`SendMessage`, `/list-agents`, `notify_when_idle` one-shot idle notice; each session binds a Unix socket (`CLAUDE_CODE_MESSAGING_SOCKET`) so "a script or hook [can] post into a session"; `-p` workers can receive messages if started with `crossSessionInbound: accept`.
- Comparison page (`/docs/en/agents`): subagents vs agent view vs agent teams vs workflows; "Agent teams don't isolate teammates in worktrees."

## 8. Recommendations

### 8.1 Which tracker is the best "source of truth" for a supervisor daemon

Requirements restated: scriptable; answers *ready*, *blocked*, *waiting on a human*, *done-but-unaccepted*; survives many concurrent Claude Code sessions writing to it.

**Pick Beads (`bd`) as the operational source of truth**, with these concrete choices:

1. **Version.** Pin **v1.2.2** (the tested recovery release) unless you need leases/CAS/HTTP, in which case run **v1.3.0-rc.1** on every client sharing the store and accept RC risk. Do not straddle versions — "Upgrade every client sharing a store together."
2. **Store mode.** Many agents on one machine → `bd init --server` (external `dolt sql-server`) or shared-server mode; embedded mode is single-writer and will throw "database is locked" under parallel `bd update --claim`.
3. **Model the four questions natively:**
   - Ready: `bd ready --json` (open, no active blockers, not wip/frozen). For dispatch use `bd ready --claim --json` (atomic) or `bd update <id> --claim --if-status open` (exit 13 on race, 1.3.0).
   - Blocked: `bd blocked --json` (dependency-blocked) plus `bd list -s blocked --json` (agent-declared).
   - Waiting on human: either custom wip statuses — `bd config set status.custom "plan_review:wip,needs_input:wip,in_review:wip"` — queried with `bd list -s plan_review,needs_input,in_review --json`; or **human gates** (`bd gate create --type=human --blocks <id>`; `bd ready --gated` / `bd gate list --json`; a human runs `bd gate resolve`). Gates are better when the blocked thing is *another* bead (e.g. the epic cannot close until a human accepts); statuses are better for the ticket's own lifecycle. `bd human list --json` is a third, label-based option for free-form questions.
   - Done-but-unaccepted: `in_review:wip` (excluded from `bd ready`, visible in `bd list`), with `external_ref` pointing at the PR; `closed` means accepted. Close policy stops `closed` while children or blockers are open.
4. **Event loop for the daemon.** `bd config set events-journal true` then `bd events tail --since <cursor> --follow` (JSON, in-transaction, with `actor`), or `.beads/hooks/on_update` for push. Fall back to polling `bd list --updated-after <ts> --json`.
5. **Acceptance criteria on the ticket.** `bd create … --acceptance "…" --validate`; `bd lint` enforces the section. This is the field your evaluator reads.
6. **Prior art to copy from.** Gas City's controller ("reconciles desired state to running state"), `gc events` JSONL/SSE, GitHub PR readiness monitors, and Gas Town's Refinery (merge queue that "runs verification gates") and `gt escalate` severities. OpenAI Symphony's `SPEC.md` (tracker `active_states`/`terminal_states`, "keeps the issue claimed and exposes it as blocked" when elicitation is needed, handoff state "Human Review") is the cleanest written spec of exactly this daemon, even though it only drives Codex.

**Runner-up: Linear**, if you want humans to live in a hosted UI. It is the only tracker that expresses all four questions with documented fields (`state.type`, `hasBlockedByRelations`, `delegate`, `AgentSession.status == awaitingInput`, `elicitation` with `select` options) — but (a) there is no server-side session-status filter, (b) Anthropic ships no Linear agent (claude-code#12925 open since Dec 2025), so your daemon must be the OAuth `actor=app` webhook receiver or you adopt Cyrus, and (c) it adds a network dependency to every dispatch decision. A pragmatic hybrid is Beads as the daemon's truth with a one-way mirror to Linear or GitHub Issues for human visibility (`external_ref` on the bead).

**Not recommended as source of truth:** Claude Code's own task list (`~/.claude/tasks/*.json`: pending/in_progress/completed + blockedBy only, session-scoped unless `CLAUDE_CODE_TASK_LIST_ID`, and the Task tools are off by default on current models) — use it only as the per-session execution ledger that `TaskCompleted` hooks can gate; GitHub Issues alone (no waiting-on-human primitive, Projects status is a second query, action runs are stateless); Backlog.md (sequential IDs across branches, no claims/leases/events — fine for one or two agents); task-master (dormant, Commons Clause); Vibe Kanban / Huly (shut down or shutting down).

### 8.2 Which process layer pairs best with superpowers (without duplicating it)

Keep superpowers as the *how*. Do **not** add Compound Engineering, BMAD, Spec Kit, CCPM or a Kiro port on top — each re-implements brainstorming → plan → implement → review and would fight superpowers' bootstrap for the same decisions. Add the three things superpowers explicitly does not have:

1. **A ticket with acceptance state (Beads), wired by a thin skill + hooks — the template-bridge pattern, done properly.**
   - Session start: `bd prime --hook-json` (SessionStart + PreCompact) so every session knows the bead it is working.
   - Intake → plan: the bead is the intake; superpowers `brainstorming` produces the spec/plan files; write their paths into the bead (`bd update <id> --design docs/superpowers/specs/… --notes plan=docs/superpowers/plans/…`) and flip `plan_review`. The human approval that superpowers already demands in chat becomes a recorded transition (`bd update <id> --status in_progress --if-status plan_review`, done by the human or by a supervisor UI on the human's click).
   - Implement: `subagent-driven-development` runs unchanged; make its "rulings" visible by mirroring the ledger to `bd comment` at each task completion (a `SubagentStop`/`TaskCompleted` hook can do this deterministically since superpowers itself emits no events — issue #1442).
   - Finish: `finishing-a-development-branch` → option 2 (PR) → bead to `in_review` with `external_ref=<PR URL>`. Never let the agent `bd close`; closing is the human's acceptance (or a merge-queue bot after human PR approval).
2. **Hard gates from Claude Code, not prose.** `TaskCompleted` (exit 2 blocks `TaskUpdate` completion; input has `task_id`/`task_subject`) and `Stop`/`SubagentStop` hooks that run the project's tests/lint *and* check the bead's `acceptance_criteria` with an evaluator subagent (Anthropic's "second opinion" pattern; the `type: "agent"` hook is experimental, so prefer a command hook that shells out to `claude -p` with `--output-format json`). `PreToolUse(Bash)` deny on `git push` to protected branches, `--no-verify`, `|| true` (block-no-verify / claude-quality-gate show the pattern; claude-code#40117 shows why). For unattended runs, `/goal "<bead's acceptance criteria> and npm test exits 0"` rather than ralph-loop's `<promise>` token. Honor `stop_hook_active` and remember the 8-block cap.
3. **External acceptance on the PR.** CI status checks + branch protection with required human approval; optionally Claude Code Review's parseable `bughunter-severity` JSON line or CodeRabbit pre-merge checks in `error` mode as an automated pre-review. This is where "done-but-unaccepted" becomes "accepted".

What to *borrow* (fields, not workflows): Compound Engineering's plan sections **Verification Contract** and **Definition of Done** and its Residual Work Gate choices (Apply / File tickets / Accept and proceed / Stop) as the vocabulary for `in_review`; Kiro/cc-sdd **EARS** phrasing for `acceptance_criteria`; BMAD's `sprint-status.yaml` status set (`backlog, ready-for-dev, in-progress, review, done`, `blocked` + `blocked_reason`) as a sanity check on your state names; Anthropic's harness posts' **sprint contract** — acceptance criteria negotiated before implementation, graded by a separate evaluator.

If you want a UI for plan approval specifically, the only software-enforced options found are Spec Kit's workflow engine (`gate` steps, `state.json`) and spec-workflow-mcp's approval dashboard; both bring their own spec pipeline, so use them only if you are willing to replace superpowers' brainstorming — otherwise a human-facing view over Beads (bv TUI, Gas City dashboard, or Linear mirror) is the cheaper path.

For running *many* controllers: use worktree-per-bead. Either `claude --bg "<prompt>" --worktree <bead-id>` under agent view (`claude agents --json` gives `state ∈ working|blocked|done|failed|stopped` and `waitingFor`, which is your liveness/"needs input" signal per session), or your daemon spawning `claude -p` per claimed bead with `--permission-mode` and `--allowedTools` set and a `Stop` hook that writes the bead transition. Agent teams are interactive-only and share one checkout, so they are the wrong primitive for a daemon; dynamic workflows have "No mid-run user input", so they fit *inside* a ticket (fan-out review/migration), not across the human gates.

### 8.3 Minimal ticket state machine for a human-supervised multi-agent setup

States (Beads status → category in brackets; every transition is a `bd update --status X --if-status Y` so races are detected):

| State | Meaning | Enter by | Leave by |
|---|---|---|---|
| `open` [active] | intake; has title, description, `acceptance_criteria` (lint-enforced), deps | human or triage agent (human confirms) | daemon dispatch |
| *ready* (derived, `bd ready`) | `open` with no active blockers and no unresolved gates | automatic | agent claim |
| `planning` [wip] | claimed; agent runs brainstorming/spec/plan in a worktree; lease + heartbeat | agent (`--claim`, `--if-status open`) | agent |
| `plan_review` [wip] | written plan/spec attached; **waiting on human** | agent | human approves → `in_progress`; human requests changes → `planning` (comment); policy may auto-approve `bounded`-labelled beads |
| `in_progress` [wip] | implementing (SDD); commits reference bead id | human (approval) or auto-policy | agent |
| `needs_input` [wip] | agent hit one of the four stop conditions or an ambiguity it refuses to rule on; **waiting on human** (`bd human`/comment) | agent | human answers → `in_progress` |
| `blocked` [wip] | dependency/external blocker; or lease expired | agent (`--status blocked`), daemon (dependency close events) | daemon: back to `open` when blockers close; `bd reclaim` on stale lease |
| `verifying` [wip] | automated gates: tests, lint, evaluator-vs-acceptance-criteria, CI; enforced by `TaskCompleted`/`Stop` hooks, not by the agent's say-so | agent (claims done) | hooks pass → `in_review`; fail → `in_progress` with findings |
| `in_review` [wip] | **done-but-unaccepted**: PR open, evidence + review report attached | hook/daemon | human accepts (PR approved & merged) → `closed`; human rejects → `in_progress`; reviewer-agent findings do not change state, only comments |
| `closed` [done] | accepted; `close_reason` = PR URL / commit | human, or merge-queue bot acting on a human-approved PR | `bd reopen` by human |
| `deferred` [frozen] / `cancelled` (`closed` with reason) | parked / dropped | human | human |

Who may transition what (the invariant that keeps the human in charge):
- **Agents** may only move forward within their claim: `open→planning→plan_review`, `in_progress→{needs_input, blocked, verifying}`, and back to `planning`/`in_progress` when a human comments. They never set `in_progress` from `plan_review`, never set `closed`, never resolve a `human` gate.
- **Humans** own every entry into `in_progress` from review states, every `closed`, `deferred`, `cancelled`, and gate resolutions.
- **The daemon** owns leases (`bd reclaim`), dependency unblocking, dispatch (claim on behalf of a spawned session), stale detection (`claude agents --json` `state=="blocked"` + `waitingFor`, Linear-style 30-min staleness), and mirroring to the human-facing tracker.

Supervisor queries that fall out of this: ready = `bd ready --json`; blocked = `bd blocked --json` ∪ `-s blocked`; waiting on human = `bd list -s plan_review,needs_input,in_review --json` (∪ `bd gate list --json` pending human gates); done-but-unaccepted = `bd list -s in_review --json`; stuck = `in_progress`/`verifying` with `lease_expires_at` past or no heartbeat.

Same machine on other trackers: Linear — `triage/backlog` → `unstarted` "Ready" → `started` states "Planning", "Plan Review", "In Progress", "Verifying", "In Review" → `completed` "Done"; `needs_input` is the agent session's `awaitingInput`/`elicitation`; blocked = `hasBlockedByRelations`. GitHub — a Project Status field with the same names, `blockedBy` for blocked, an open PR for `in_review`, `needs-human` label for `needs_input`/`plan_review`.

Three rules that matter more than the state names: (1) acceptance criteria are written *before* `planning` leaves `open` and are what `verifying` grades — by a fresh-context evaluator, not the implementer; (2) `verifying` is a hook/CI outcome, never an agent assertion; (3) `closed` is a human act (or a bot acting on a human-approved PR), so "done-but-unaccepted" is always observable as `in_review`.
