## The inbound channel does not work on this Mac, so Ambrosio reads Messages itself

`bin/ambrosio inbox` and the `inbound` field of `bin/ambrosio tick` read the Messages database directly (`src/inbox.ts`). This is not redundancy for its own sake — the official iMessage channel plugin cannot deliver a self-chat message on this machine at all.

The plugin drops every `is_from_me=1` row (`server.ts:797`), on the assumption that a self-chat message also arrives as an `is_from_me=0` copy which its `consumeEcho` check then sorts out. That assumption fails when the Apple ID is an email (`E:jaime.fjorge@gmail.com`) but the self-chat is a phone number: Messages files the message as an ordinary outbound DM and never writes the second copy. Every command was being discarded before it reached the reply grammar, with no error on either side.

Two things make the direct reader safe:

- **It never reads Ambrosio's own sends back.** `imessage.send` records each message before it goes out, and `readInbound` drops anything matching a recent send. Without this the manager would answer its own digests in a loop.
- **It cannot replay history.** The first read looks back 15 minutes; after that a row-id cursor decides, so nothing is missed however long Ambrosio was down, and nothing is handled twice.

Modern macOS also leaves `message.text` NULL and puts the body in `attributedBody` as a typedstream blob, which `parseAttributedBody` decodes.

## Two bugs the rehearsal caught

Both would have silently put **two workers on one ticket**. Both are guarded in code and covered by tests.

1. **`claude --bg --resume <short job id>` starts a copy.** It needs the full session UUID. `agents.resume` now refuses anything that is not a UUID.
2. **A session in state `blocked` still has a live process,** so resuming it forks too. `blocked` means waiting for input, not exited. `agents.resumeStopped` stops the session first, which is what makes the resume continue it under the same id.

A third finding, not a bug: **background workers edit in `.claude/worktrees/<ticket>/`, never the main checkout.** Review the branch or the PR. An early verification looked in the main tree and wrongly appeared to show no work.

## Not built yet

- **Linear bridge.** Linear is where the real work lives. v1 should pull issues and their context into Beads tickets (`external_ref`), and push status plus a summary comment back on each transition. Linear is a source and a report target, never a bus between agents.
- **Permission relay over the channel**, so a blocked permission prompt can be approved from Messages instead of only being reported.
- **Verity verdict read from its API** rather than reported by the worker.
- **`/goal`**, deliberately unused in v0: it was judged unreliable for completion, so verification is explicit commands plus a fresh-context reviewer plus a Verity PASS.

## Known limitations

- **Tickets do not travel between machines.** Beads is stealth mode, so its database is local. See `docs/SECOND-MACHINE.md`.
- **One manager machine only.** Two tick sessions would double-send digests and could double-dispatch.
- **iMessage is macOS-only.** Telegram is the drop-in swap elsewhere.
- **N workers burn quota N times as fast.** That is what the WIP limit is for.
- **Research-preview surfaces.** Agent view and channels may change; the code is thin on purpose so a change costs a script, not a rewrite.
- **The urgency filter is a keyword floor,** deliberately narrow. It will miss things. Anomalies and permission denials are the other escalation paths.

## Open questions for the first real day

1. Does the hourly cadence feel right, or should the digest be every two hours with urgent-only in between?
2. Do workers ask too much, too little, or about the wrong things? Every unnecessary question is a ticket-writing bug worth fixing at intake.
3. Is a WIP limit of 3 the right number for one person's attention and quota?
4. Does the plan-review gate earn its place, or should more tickets be bounded?
